# ADR 0002：可重放 Agent 内核的事件结算

状态：已接受

## 背景

第一阶段内核需要同时支持流式模型输出、工具循环、取消和失败恢复。若直接修改消息数组，运行中断后就无法区分已经向用户展示的临时内容、已经提交的模型消息和仍未结算的工具调用。

## 决策

会话使用严格单调 sequence 的 append-only 事件信封。只有完成的用户消息、assistant 消息和工具结果进入模型消息投影；流式增量只作为进程内观察通知。失败或取消的 assistant 尝试仍以 `assistant.settled` 事件记录其部分文本和已观察到的工具调用，但不会进入后续模型请求。

Agent 使用显式 `idle` 和 `running` phase。每个已开始的 turn 和 step 在成功、失败或取消路径上各写入一个结束事件。模型输出的工具调用先随完成的 assistant 消息持久化，随后按顺序执行；每个工具调用都产生成功、失败或取消结果，结果写入后才能开始下一次模型请求。

`session`、`model` 和 `tools` 分别拥有自己的 capability 接口，Agent 通过构造参数接收它们。第一阶段使用内存会话、脚本模型和顺序工具执行，不包含真实模型、网络 host、文件持久化或动态插件系统。

## 后果

任何模型请求都可以从持久事件确定性重建，测试也能直接验证生命周期闭合。失败尝试保留审计信息，同时不会把不完整 assistant 输出误送回模型。顺序工具执行易于理解，但暂时无法并行执行彼此独立的工具；持久存储和并发调度需要后续 ADR 定义写入所有权与顺序语义。

## 放弃的方案

- 直接维护可变消息数组会丢失失败与恢复所需的执行事实。
- 持久化每个流式 token 会放大会话日志，并把 UI 传输细节固化为存储协议。
- 第一阶段引入通用插件上下文或并行调度会掩盖 Agent 状态机和事件结算的核心机制。
